# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo holds two unrelated things:

1. **`webapp/` + root config** — an SAP Fiori List Report app (UI5 1.114.9, `sap_horizon` theme) generated by SAP Fiori tools. It is bound to the OData service `ZSUI_SALES_ANALYSIS_BIND` on the ABAP backend `hilmar.sapvista.com:50000`, main entity `ZCSSV_Sales_Analysis`.
2. **`day-05/`** — a Python "Autonomous Procurement Agent" capstone (see `day-05/README.md`). Plus a standalone ABAP report, `zsv_po_open_list.abap` (untracked, at root).

`ai-guardrail-agent/` is an empty directory.

## Commands

### Fiori/UI5 app (run from repo root, requires Node LTS and `npm install`)

- `npm start` — `fiori run` against the real backend via the `S4H` destination (needs backend access).
- `npm run start-mock` — uses `ui5-mock.yaml` with the `sap-fe-mockserver` and generated mock data from `webapp/localService/mainService/metadata.xml`. Use this when the backend is unavailable.
- `npm run start-local` — uses `ui5-local.yaml` (SAPUI5 libs declared locally instead of loaded from ui5.sap.com).
- `npm run build` — `ui5 build` into `dist/`.
- `npm run lint` — `eslint ./` using `@sap-ux/eslint-plugin-fiori-tools` recommended rules (`eslint.config.mjs`).
- `npm run deploy` — `fiori verify`. `deploy-config` adds a deploy configuration.

There is **no test framework or test script** in this repo. Running a single test is not applicable; `npm run lint` is the only automated check.

### CAP service (`phase-3/`, separate `package.json`)

- `cd phase-3 && npm install` first. Then `npm start` (`cds-serve`) serves OData V4 at `/odata/v4/po/PurchaseOrders` on port 4004.
- `npm test` runs jest: `test/validate.test.js` (pure rules) and `test/po-service.test.js` (HTTP via `cds.test`).
- Validation lives in `srv/validate.js` and is wired in `srv/po-service.js`. An empty vendor name or quantity <= 0 returns HTTP 400.

### Python agent (`day-05/`)

No dependency manifest exists. The README expects `ANTHROPIC_API_KEY` to be exported.

- Run from inside `day-05/`: `python agent.py`. The paths `audit.jsonl` and `pos.json` are relative to the current directory, so running from the repo root writes the audit log in the wrong place.
- `tools.py` has no `__main__` entry point and is imported, not run directly.
- There are no tests or linters configured for Python.

### ABAP

`zsv_po_open_list.abap` is an ABAP report (SELECT-OPTIONS + `cl_salv_table` ALV). It cannot be built or run locally; it must be imported into an SAP system.

## Architecture

### Fiori app

- `webapp/index.html` bootstraps UI5 with `ComponentSupport`, which instantiates `webapp/Component.js` (`project2.Component`, extends `sap/suite/ui/generic/template/lib/AppComponent`).
- The app is configured almost entirely in `webapp/manifest.json`, not in JavaScript. It is a generated Smart Template (`ListReport|ZCSSV_Sales_Analysis` → `ObjectPage|ZCSSV_Sales_Analysis`), so pages, routing, and table settings live in `sap.ui.generic.app` in the manifest.
- Data sources: `mainService` (OData V2, `/sap/opu/odata/sap/ZSUI_SALES_ANALYSIS_BIND/`) with two annotation sources: `annotation` (`webapp/annotations/annotation.xml`) and `ZSUI_SALES_ANALYSIS_BIND_VAN` (`webapp/localService/mainService/ZSUI_SALES_ANALYSIS_BIND_VAN.xml`).
- `webapp/localService/` holds the metadata and annotations copied from the backend. Metadata is used by the mock server and the local preview.
- The UI5 dev server stack is in the `ui5*.yaml` files. Each has the `fiori-tools-proxy` middleware, which forwards `/sap` to the backend. The mock files add `sap-fe-mockserver` ahead of `csp`. Changes to the backend contract require regenerating or updating `localService/` and the annotation XML, not only editing the manifest.
- `ui5.yaml` `builder.resources.excludes` keeps `/test/**` and `/localService/**` out of the build.

### Procurement agent (`day-05/`)

- `tools.py` holds the business logic and the tool layer: `list_open_pos`, `get_po_status`, `draft_email`, `send_email`. It also has `TOOLS`, the Anthropic tool-use JSON schema list, and `run_tool()`, the dispatcher. Every tool call appends a record to `audit.jsonl` via `log_audit()`.
- `pos.json` is the mock PO data source (`po_number`, `vendor_name`, `due_date`, `delivered_qty`, `total_qty`).
- `agent.py` is **not yet a real agent**. `run_agent()` is a 10-step loop that hard-codes two steps: `read_system_data("404")`, then `send_email(...)`. It does not call the Claude API and does not import `tools.py`. Its `send_email` and `log_audit_event` duplicate the versions in `tools.py` with different signatures and audit schemas. Treat the two files as separate prototypes; wiring them together is the open work.
- Human-in-the-loop is enforced in code, not in prompts: `send_email` in both files blocks on `input()` for a `y/n` answer before anything is marked sent. Keep that gate in code if the agent is extended.
- `audit.jsonl` is append-only. Both files write to it with different record shapes (`action`/`details` in `agent.py`, `tool`/`inputs`/`result` in `tools.py`). Don't assume one schema when reading it.

### ABAP report

Reads `EKKO` joined to `EKPO` on `EBELN`, filtered by vendor (`LIFNR`) and document date (`BEDAT`) select-options, and shows the result in a `CL_SALV_TABLE` ALV. Note that `lv_lifnr` is typed `ELIFN` and `lv_bedat` `EBDAT`, and that `CATCH cx_salv_msg` is the only error handling.
